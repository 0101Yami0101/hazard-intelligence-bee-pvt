2The shell, and how a module joins

app.py is only a shell: home page and router. It knows nothing about landslides or floods. Every module is one entry in products/__init__.py. Tap one:

adding a module
1 folder + 1 entry
products/<slug>/ with view.py (a render(shell)) and assets/<slug>/. The tiles, side menu and home page read the list; none of them name a module.
loaded late
Only the opened module
A module's code is imported inside render(), so the home page doesn't pay for every module's maps.
loaded once
The Shell object
Grid, geography, elevation and the visitor's place are loaded once by app.py and handed in. A module never loads the grid itself, so two modules can't disagree on where Arunachal is.
🔗 The module is in the address: ?m=flood. A link to FloodSense stays a link to FloodSense, and the back button moves between modules.

The one live call the app makes itself. One fetch serves SlideSense and FloodSense. SoilSense makes its own for Assam.

1 hcache, shared by every visitor

So 10 visitors or 10,000 cost the same: at most 13 calls an hour per running copy of the app. A failed call is retried 3 times with growing waits before the page gives up.

rule
One source, end to end
The live rain is scored against Open-Meteo's own past, not IMERG. Open-Meteo runs 1.68× wetter than IMERG, and the two agree poorly day to day (0.32). Mixing them gives confident wrong numbers. Open-Meteo's archive and its forecast's past days match (ratio 1.00).
checked
The switch didn't cost skill
The landslide trigger scored 0.768 on IMERG and 0.764 on Open-Meteo (84 events). Percentiles rank wet days alike even when the millimetres differ.

5The daily run in the cloud

Moved off the PC on 20 Oct 2026, because the PC missed 1, 3, 13 and 15 Oct and often ran hours late. A missed day can never be graded.

08:30 ISTModal starts the jobin Mumbai, on the pankajkarjay workspace
fetchRain, river gauges, soil wetnessOpen-Meteo · CWC + NWDP · Earth Engine (robot key in a Modal secret)
~1 minFlood models runflood_forecast_live.py, the same script the PC runs
logWrite the day, grade yesterdayflood and landslide logs, kept on a Modal storage volume
publishOne snapshot at one linklive_forecast.json, read-only
≤ 1 h laterThe app picks it upfeed.py fetches it if it's a newer issue. No push, no restart.
trap 1 · found while building
CWC doesn't answer from abroad
From US, Tokyo and Jakarta machines every gauge request hung for 60 s. From Mumbai: about 1 s. So the job is pinned to India (1.75× the price), and a run with no fresh CWC gauge is retried.
trap 2 · found while building
Some machines gave different numbers
Machines with AVX-512 chips rounded the last digit differently (2 of 5 failed the same-numbers check). Fixed by switching those routines off in numpy: then 8 of 8 matched the PC exactly.
cost
Under $2 a month
About 53 s a run. Free plan with $30 a month of credit.
⚠️ The cloud runs the copy uploaded at the last deploy, not the PC's files. After any change to the forecast code or a model: record on the PC → seed --what golden → ::golden --times 4 → modal deploy.

📦 v2 gets app files only: webapp/, requirements.txt, runtime.txt, .streamlit/. Models, logs, training code and internal docs stay private.
🚫 Never records/ or flood_intake.py on a deployed branch. Together they make the hosted app show a flood report form that saves to a disk the host wipes. Reports would vanish.

9One v2 deploy, start to finish

The roadmap's exercise: do this once yourself, with Claude watching. It updates v2 without touching your local branch or your ~240 uncommitted files, using a temporary index.

⚠️ Step 5 publishes to a public repo and changes the live app. Only with the user's say-so.
1 · All screens open, no errors (expect "PASS", 58 screens)
.venv\Scripts\python scripts\run\check_app_screens.py
2 · Same check on the host's newer packages (clean venv at C:\hv_1011; Streamlit 1.66.1 / pandas 3.1.0 on 31 Oct)
C:\hv_1011\Scripts\python scripts\run\check_app_screens.py
3 · Build the new v2 tree in a temporary index (PowerShell). Nothing is published yet.
git fetch origin; $env:GIT_INDEX_FILE = "$env:TEMP 2.idx"; git read-tree origin/v2; git add webapp requirements.txt runtime.txt .streamlit; $t = git write-tree; Remove-Item Env:GIT_INDEX_FILE
4 · See exactly which files would change. Read the list: no records/, nothing internal.
git diff --stat origin/v2 $t
5 · Make the commit on top of v2 (short message) and push it by its hash
$c = git commit-tree $t -p origin/v2 -m "One short sentence"; git -c http.version=HTTP/1.1 push origin "${c}:refs/heads/v2"
6 · Watch the app rebuild (about 2 min), then open each module once on the live link

Pushes over ~10 MB fail from this PC (timeout, then a 403 for a while): push one folder per commit. Your local main and working files are never touched by steps 3–5.

11The operations limits card

🌧️Open-Meteo free tier is non-commercial. Paid: a paid plan before a paying client, which also allows finer (~11 km) rain.
🔕Nobody is alerted when the daily run fails. It shows only in Modal's dashboard and status.json (::pull). Free: add an alert.
💤The free host sleeps when unused. The first visitor waits for it to wake, and up to 10 s for today's forecast.
🧠Free host memory is tight (the docs plan for 1 GB). Biggest load: SoilSense's 13 maps, about 55 MB, only when opened.
🔁Two daily runs still exist (PC + cloud) until the week's result is recorded and the PC task is switched off.
🛰️Earth Engine on a restricted, non-commercial quota. Fix before commercial use.
🧪A research prototype, not a safety tool. The app doesn't send warnings to anyone.
🌍CWC gauges need an India-based machine. Moving hosts outside India silently drops them.
