0Say what the backbone is: one definition, the right words, and APSSDI

Before the details, be able to say what we're building in one sentence, name the kinds of data it holds in standard terms, and explain why it isn't APSSDI. Worked out on 4 Nov 2026. Data groups and counts are from webapp/assets/backbone/catalogue.json; APSSDI's contents are from our check of its open map server on 3 Nov (apsac.html).

The backbone is a workshop. It collects data about the ground, water and weather, checks it, lines it all up on one map, keeps it fresh every day, and checks every forecast against what really happened.

The definition

full version · say this when there's time"A data backbone that takes scattered data about the ground, water and weather, checks it, lines it all up on one map of the state, and keeps it updated every day, so hazards can be forecast for any place, and every forecast is checked against what really happened."
short version · one breath"A living, forecast-ready data backbone: every source checked, lined up on one map, updated daily, and graded against what really happens."
🏷️ As a title or a slide line: "A geospatial data backbone for hazard forecasting." The briefing's version, "the data backbone for mountain-hazard intelligence", says the same thing and is still fine.
The World Engine in one breath: it brings in the loot, checks it for Glitches, snaps it onto one set of blocks, refreshes it every morning, and keeps score of every prophecy.

🎮 Blockland: the library and the workshop

The Sky-Eye Guild (APSAC) keeps a big map library called APSSDI. It's full of useful scrolls: rock maps, fault cracks, village lists, hospital lists. Each scroll is drawn in its own style and size, and they don't change much.

Our World Engine is a workshop, not a library. 🎮 the loot run

Each chest has its own little bot (a fetch script). The bot goes to one Guild, downloads only Blockland's part of the map, and puts the loot in the 🔐 Vault exactly as it found it. Then it writes a 🏷️ tag: where it got it, the link, the date, the rules for using it, and a fingerprint of the file.

Why so careful? Because if anyone ever asks "where did this number come from?", you can follow the tag all the way back to the Guild that made it.

Fetch scripts download each source for the state's box and call record(), which writes _SOURCES.json (source, link, fetch time, terms, and a checksum per file). Raw files are never edited and aren't in git. Only the daily forecast run is automatic.
Why keep the raw file untouched, instead of cleaning it straight away?
So you can always start again. If a later step has a bug, you fix the step and rebuild from the original. And you can prove where every number came from.
A scientist asks "where did the rock type for this block come from, and when?" How do you answer?
Follow the tag: the rock map came from APSSDI (APSAC's portal), fetched on 4 Nov 2026; the tag holds the link and a fingerprint of the exact file. Every source has one.

3The law: six frozen choices

From DATA_CONTRACT.md. Changing any of them means rebuilding everything. 🔒 means changing it after a model exists would void every number we've published.

Six rules are frozen, like the rules printed on a board game's box. Change one, and every block in the world has to be rebuilt, and every score we've published stops counting.

1 · map projection
UTM zone 46N
Raw data comes in degrees, and a degree isn't a fixed distance. In metres, "500 m from a road" is easy. Arunachal spans two zones, but the error is 0.4%.A ruler, not degrees. A degree of longitude isn't the same length everywhere. Metres are, so "500 m from a road" is easy to measure.
2 · square size
100 m
30 m = 91 M squares, too slow. 250 m blurs the steep face that actually fails. 100 m = 8.2 M, fits in memory.A football field per block. Smaller means too many blocks to play with; bigger hides the steep cliff that actually falls.
3 · starting corner
x 350,000 · y 2,950,000
A round number fixed by hand, not taken from the border file. If the border file changed, a computed corner would shift every square silently.The corner stone, nailed down by hand. If it were worked out from the border file, a new border file could quietly slide the whole world.
4 · square ID
row × 100,000 + col
You can decode any ID in your head, so a bad join shows up at once. Try it in section 4.A cinema seat number. Row and seat glued together. You can read any block's address in your head.
5 · column names
group_name_unit
soil_bdod_0-5cm_cgcm3. The unit is in the name because a soil density of "107" once fooled us: it is centigrams, not grams.Always write the unit. Like writing "cm" after a height. A soil density of "107" once fooled us.
6 · test blocks
50 km → 5 groups
Fixed seed 42, frozen before any model was trained, with a fingerprint (ce08e9f0124386ac) to prove it. Otherwise you'd pick blocks that flatter the model without noticing.The 🏋️ surprise-exam regions, sealed in an envelope. Chosen and fingerprinted before any training, so nobody could pick easy ones later.
⚖️ If the doc and the code disagree, the code wins. scripts/build/grid.py is the single source of truth. The doc only explains why.
🎮 the gamerules

Every board game has rules printed on the box. Blockland has six, and they're frozen. They decide how the world is measured (metres), how big a block is (100 m), where the world's corner is, how each block's address is written, how each fact is labelled, and which regions are kept back for the surprise exam.

Why freeze them? Because every model, every score and every forecast is built on top. If you moved the corner by one block, every block would get a different address, and nothing would line up any more.

From DATA_CONTRACT.md: UTM 46N, 100 m squares, a fixed origin (350,000 / 2,950,000), cell ID = row × 100,000 + col, column names group_name_unit, and test blocks of 50 km in 5 groups (seed 42, fingerprint ce08e9f0124386ac). scripts/build/grid.py is the source of truth.
Why was the world's corner typed in by hand, instead of taken from the state border?
If it came from the border file, a new or corrected border file would quietly shift every block. Typed in by hand, it can never move.
What does the 🔒 on rule 6 mean?
The test regions were sealed before any model was trained. Changing them now would make every published score meaningless, because you could be choosing regions that flatter the model.

4Decode a square ID

Every row in the big table has a cell ID. Type one, or click a town. The ID tells you exactly where the square is.

Every block has an address number. Cut off the last five digits and you get its row and its column, like a row and seat number in a cinema.

Try it: 222402305 → row 2224, seat 02305 → 222.4 km down from the top edge, 230.5 km across from the left → the hillside above Ziro (section 8).
🎮 reading a block's address

Blockland is a giant cinema with 3,200 rows and 5,900 seats in each row. Every block's address is its row number followed by its seat number (always 5 digits). Row 0 is the top (north) edge. Each step is 100 m, so row 1,000 is 100 km south of the top edge.

Cell ID = row × 100,000 + col. Row 0 is the north edge of the grid box; each step is 100 m in UTM 46N. You can decode any ID in your head, so a wrong join shows up at once.
Where is block 100002000?
100002000 ÷ 100,000 → row 1000, column 2000: 100 km down from the north edge and 200 km across from the west edge.
Why not just number the blocks 0, 1, 2, 3…?
A simple counter can't be read in your head, and if the grid ever changed, every number would shift silently and joins would go wrong with no error. Row-and-seat can always be checked.

5The 34 facts, in six families

Every square gets these 34 columns. Hover a chip to read what it means. Most come from just two downloads: the height map and the soil map.

Every block carries a 🎒 backpack of 34 facts: how steep it is, how wet, how far from a road, what grows there, what rock and soil it's made of.

➕ Also on the grid, but not among the 34: HAND and the size of the nearest channel (built later for FloodSense), and the rain index (section 7). The 34 are the landslide model's inputs. Each product reads the columns it needs.Extra pockets. HAND (for FloodSense) lives on the grid too, and rain lives in its own stack. The 34 are just the ones SlideSense reads.
🎮 opening one block's backpack

Every one of the 8.2 million blocks carries the same backpack with six pockets. 28 of the 34 facts come from just two chests: 10 from the ground-height chest (shape and water) and 18 from the soil chest (6 soil things at 3 depths). Hover a chip above to see what each fact means.

34 columns per square: 8 terrain, 2 hydrology, 3 distances, 1 land cover, 2 geology, 18 soil (6 properties × 3 depths). 10 come from the Copernicus DEM and 18 from SoilGrids. They're the landslide model's inputs.
Why does the soil pocket hold 18 facts, when there are only 6 soil things?
Each of the 6 (clay, sand, silt, density, stones, organic carbon) is measured at 3 depths: the top 5 cm, 15–30 cm and 60–100 cm. 6 × 3 = 18.
Why isn't rain one of the 34?
Rain changes every day. The 34 describe the ground, which barely changes. Rain lives in its own stack, and each block just remembers which rain slab it sits in (section 7).

6Three moves turn any shape into a column

Sources come as grids, outlines or lines. Each has its own move to land on the 100 m squares.

Data comes in three shapes: grids (like pixels), outlines (like countries on a map) and lines (like roads). Each shape has its own trick for landing on our blocks.

🔲 Grid → grid
A coarse grid (soil at 250 m) is spread over the squares it covers. A fine one (height at 30 m) is worked out first, then averaged: slope is worked out at 25 m and then averaged, so steep faces aren't smoothed away.
Pouring. A big soil pixel pours its value into every block under it. Tiny height pixels are turned into steepness first, then averaged, so a cliff stays a cliff.
🧩 Outline → label
A rock map is a set of outlines. Each square asks "which outline am I inside?" and stores that rock's code.
"Which country am I in?" Each block checks which rock outline it's standing inside, and writes down that rock's name.
📏 Line → distance
A road, river or fault is a line. Each square stores "how far to the nearest one". This is measured on the full box, so a square near the border still finds a road just across it.
"How far to the nearest road?" Each block measures it, even if the road is just over the border.
🎮 three snapping tricks

The loot arrives in three shapes, and the World Engine has one trick for each. Pour a grid onto the blocks. Ask "which outline am I in?" for shapes. Measure "how far to the nearest one?" for lines. Every chest, whatever shape it came in, ends up as one column in the backpack.

Raster → raster (resample, or derive first then aggregate), polygon → label (point in polygon), line → distance (distance transform on the full box, not the state mask).
Why work out the slope before shrinking the height map to 100 m?
Averaging heights first flattens the hill: a steep 25 m face inside a gentle 100 m square disappears. Working out slope at 25 m and then averaging keeps the steep bits, and steep faces are what fail.

7Rain is special: never copied onto the 100 m squares

Copying rain onto every square would mean 8.2 M squares × 9,555 days = 78 billion numbers, about 12,000 copies of each rain value. So we don't.

Rain is too big to copy onto 8.2 million blocks for 9,555 days. So each block just remembers which rain slab it sits in, like knowing your class number instead of copying the whole timetable into every pupil's notebook.

The trick: one file, imerg_index.tif, stores for every 100 m square which rain square it sits in. Models join on (rain square, date). It holds the same information with four orders of magnitude less storage.

It's also honest. A 100 m rain map would look sharp and invite people to trust it at 100 m. It's 11 km data.

No fake sharpness. Painting 11 km rain onto 100 m blocks would make it look sharp, and people would trust it more than they should.
📚 Rain history
NASA IMERG, ~11 km squares, 2000-06-01 → 2026-07-29, 9,555 days, zero gaps. 892 rain squares cover the state. The whole archive is only 326 MB, and downloading it is a ~2-hour job.
📡 Live rain + 7-day forecast
Open-Meteo, a free weather service, at 219 points about 22 km apart. One fetch feeds both forecasts. Points are spaced that far apart because of the free tier's limits: a budget limit, not a science limit.Free-plan spacing. 219 rain points, about 22 km apart, because that's what the free plan allows. 🎮 the rain slabs

Over Blockland, the sky is cut into big rain slabs, each about 11 km wide. About 12,000 blocks sit under each slab. Copying every slab's rain onto every block, for every day since 2000, would mean 78 billion numbers. So each block carries just one tiny note: "my rain slab is number 1285". When a Guardian needs the rain, it looks up the slab.

imerg_index.tif stores, for every 100 m square, which 11 km IMERG cell it sits in; models join on (rain cell, date). IMERG: 2000-06-01 to 2026-07-29, 9,555 days, no gaps, 892 cells over the state. Live rain: Open-Meteo at 219 points ~22 km apart (a free-tier limit).
Why not just copy the rain onto every block?
Two reasons. Size: 78 billion numbers, about 12,000 copies of each value. Honesty: a 100 m rain map would look far sharper than 11 km data really is.
Is the 22 km spacing of the live rain a limit of science?
No: it's the free plan. A paid weather plan, or IMD's gauges through an Ask, would make it finer. Say what lifts a limit; never call a free-tier limit permanent.

🧩 One lattice. Both corners are whole multiples of 10 km, so where the two boxes overlap, Assam's squares sit exactly on Arunachal's. A river that crosses the border can be stitched square by square.Two boards, one pattern. Lay two chess boards so they overlap. 🎮 the painted-on locks

A website might say "no data" or "login needed". But the map you see on that website has to get its pictures from somewhere. Look at where they come from, and you often find an open door: the server that feeds the map, which anyone can ask.

12Checked before trusted: real catches

Rule 3 in action. Each of these would have quietly poisoned a model.

Every chest gets scanned for 👾 Glitches before a Guardian is allowed to learn from it. Even official chests.

Official flood map on cliffs
70.5% of Bhuvan's "flooded" pixels were on slopes over 15°. It's a rendered picture, smeared at the edges. Declared unusable as truth.👾 Water on cliffs. Water can't sit on a cliff.
GSI's map came out scrambled
Exported in one big piece, the national susceptibility map matched its own source on only 41% of squares. Fixed by downloading in tiles on the server's own grid, then checking a small tile against a big one.👾 The scrambled puzzle. One big download came out jumbled; small pieces came out right.
Landslides outside the state
GSI sends data by map sheet, not by state: 246 of its polygons were in Nagaland and Assam. Filter by state before counting.👾 Visitors from next door. Some craters were in Nagaland and Assam.
One wrong river reading = a "52% flood"
A single bad gauge value looked like a flood. Now a three-pass spike filter cleans readings, and it has found 18 false high-water days.👾 One broken height stick. One bad reading looked like a flood.
Soil density of 107
That's centigrams per cm³, i.e. 1.07 g/cm³. Hence the unit in every column name.👾 The missing "cm". 107 what?
Rain "holes" that weren't
Four missing days were our own version bug, not NASA's. Re-check before declaring data missing.👾 Fake holes. Our bot's bug, not NASA's.
🎮 the Glitch scanner

Before any chest reaches a Guardian, you scan it. Does the water sit where water can sit? Are the craters inside Blockland? Does one weird reading stand out? Do the units make sense? Each Glitch above would have taught a Guardian something false, without any error message.

Rule 3 of the backbone: check before you trust. Six real catches: Bhuvan's flood map on slopes, GSI's scrambled export, polygons outside the state, a single bad gauge reading (now a three-pass spike filter), soil density units, and our own fetch bug.
Why is the unit written in every column name?
Because a soil density of "107" looked like grams but was centigrams per cm³ (1.07 g/cm³). With the unit in the name (…_cgcm3), nobody can misread it again.
